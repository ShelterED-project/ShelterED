# ShelterED

Offline-first освітній хаб для укриттів. Уроки, тести та перекличка класу працюють без інтернету й синхронізуються з хмарою, коли зʼявляється мережа.

Це навчальний командний проєкт: 6 розробників, 2 місяці (демо 12 грудня 2026). Повне технічне завдання: `docs/tz.md`. Якщо ця інструкція суперечить ТЗ, спитай мене, а не вгадуй.

## Проблема й мета

Через повітряні тривоги та відключення світла діти годинами сидять в укриттях без зв'язку й втрачають навчання. Zoom і Google Meet без інтернету не працюють. ShelterED має дозволити продовжити урок в укритті без мережі, відмітитися в перекличці та не втратити жодних даних.

Головний сценарій MVP: тривога починається посеред уроку → учні в укритті продовжують урок з матеріалами, які підготував вчитель → клас відмічається «я в укритті» → результати лишаються на пристроях і локальному сервері → з появою мережі все синхронізується в хмару без втрат і дублів.

## Стек

- **Frontend:** React, TypeScript, Vite, Tailwind CSS, Redux Toolkit / RTK Query, `vite-plugin-pwa` (Workbox), IndexedDB (через `idb` або Dexie).
- **Backend:** Python, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic, PostgreSQL, Celery + Redis.
- **Авторизація:** JWT, OAuth 2.0 PKCE, ролі.
- **AI:** RAG-пайплайн, хмарна LLM через API, легка локальна модель на ноутбуці вчителя (її вибір ще не затверджено).
- **Локальний сервер:** Python (C++ лише за потреби), Wi-Fi точка, локальний вебсервер, локальна БД.
- **DevOps:** Docker, Docker Compose, Nginx, GitHub Actions, GHCR.
- **Якість:** Ruff або Flake8, pytest, oxlint, Prettier, Playwright для E2E.

## Архітектурні принципи (обовʼязкові)

Усе нижче випливає з offline-first. Порушення цих правил ламає головну фічу проєкту, тому звертай на них особливу увагу.

1. **Інтерфейс читає з локального сховища, а не чекає мережу.** Компоненти не викликають `fetch` напряму: усі дані йдуть через єдиний шар даних (RTK Query + локальне сховище). Екран має працювати з даними, які можуть бути застарілими або ще не відправленими.
2. **Ідентифікатори створює клієнт (UUID)** ще до відправки на сервер. Сервер приймає їх як є.
3. **Запити на запис ідемпотентні.** Повторна відправка тієї самої події не створює дублів і нічого не ламає. Це критично для синхронізації.
4. **Кожна дія учня фіксується як подія** (з унікальним id і часом) і потрапляє в чергу відправки (outbox) в IndexedDB. Подія залишається в черзі, доки сервер не підтвердить її отримання.
5. **Синхронізація йде пачками.** Спочатку на локальний сервер укриття, звідти в хмару. Сервер приймає події в порядку їхнього часу й ігнорує вже отримані за id.
6. **Нічого не губимо.** Жодна відповідь учня й жодна відмітка переклички не можуть зникнути при обриві мережі, перезапуску пристрою чи ноутбука.
7. **Запасний канал:** якщо немає ні інтернету, ні локального сервера, прогрес передається через QR-код.

## Frontend: правила

- Мова інтерфейсу: українська за замовчуванням.
- **Енергоменеджер:** темна тема за замовчуванням в режимі укриття, мінімум анімацій, мінімум фонових запитів.
- **Тихий режим:** усе відео має субтитри, кожне завдання можна пройти без звуку, жодного обовʼязкового звуку.
- Мобільний пріоритет: недорогі Android-телефони й планшети, Chrome та Safari. Великі елементи керування, зручні для дитини.
- Сторінки й навігація залежать від ролі: учень, вчитель, батьки, адміністрація школи.
- Мікромодулі навчання короткі (3–5 хвилин), мають відкриватися менш ніж за 2 секунди.
- Для iOS: не покладайся на Background Sync. Відправляй чергу, коли користувач відкриває застосунок.
- Кеш Service Worker версіонується разом із пакетами знань, щоб після оновлення уроку не показувалась стара версія.
- Типи TypeScript строгі, `any` не використовуємо без коментаря, чому.

## Backend: правила

- Усі зміни схеми БД лише через міграції Alembic. Не змінюй таблиці вручну.
- Контракт API описує OpenAPI-специфікація (`docs/openapi.yaml` або згенерована FastAPI). Змінюючи API, одразу оновлюй специфікацію й повідомляй команду фронтенду.
- Ендпоінти запису приймають клієнтські UUID і є ідемпотентними.
- Права перевіряються на рівні API за роллю та належністю (вчитель бачить лише свої класи, батьки лише свою дитину, учень лише свої дані).
- Фонові задачі (синхронізація, вебхуки) через Celery + Redis.
- Пароль, ключі й токени ніколи не потрапляють у логи.

## Ролі й доступ

| Роль | Може | Не може |
| --- | --- | --- |
| Учень | Проходити уроки й тести, відмічатися в перекличці, питати ШІ-репетитора, бачити власну мапу знань | Бачити дані інших учнів |
| Вчитель | Створювати й публікувати уроки, бачити статус і прогалини свого класу, запускати перекличку, синхронізувати локальний сервер | Бачити чужі класи |
| Батьки | Бачити статус безпеки й прогрес своєї дитини | Бачити інших дітей |
| Адміністрація школи | Дашборд безпеки, журнал тривог, керування класами | Редагувати навчальний контент вчителів |

## AI-модулі

- Репетитор пояснює пропущену тему іншими словами й розбирає помилки в тестах. В укритті працює на локальній моделі або закешованих поясненнях.
- Опитування «як ти зараз?» **не ставить діагнозів** і не оцінює стан дитини як медичний. Збирається мінімум даних, показуються лише узагальнені сигнали, і система делікатно пропонує звернутися до шкільного психолога. Формулювання питань погоджуються з психологом.
- Парсинг сповіщень про тривоги має валідацію. Якщо API недоступне або змінило формат, залишається ручна кнопка «Тривога» для вчителя.

## Безпека даних дітей

- Збирай і зберігай мінімум персональних даних. Не додавай нових полів про дітей без обговорення.
- Дані психологічного опитування бачать лише уповноважені особи.
- Секрети (ключі AI, паролі БД) лише в `.env`, який не комітиться. У репозиторії тільки `.env.example` без значень.
- Шифрування в дорозі. На локальному сервері потрібен HTTPS (інакше Service Worker не працює), тому це перевіряємо в першому спринті.

## Робочий процес

- Гілка `main` відкрита для прямого пушу, усі в команді можуть пушити в неї. Перед пушем роби `git pull --rebase`, щоб не перетирати чужі зміни.
- Для більших або ризикових змін можна використати гілку `feature/<короткий-опис>` і pull request з рев'ю.
- Повідомлення комітів короткі й змістовні: що змінено і навіщо. Українською або англійською, але однаково в межах PR.
- В описі PR: що зроблено, як перевірити, чи змінився API (і чи оновлено OpenAPI). Привʼязуй до завдань: `Closes #<номер>`.
- Завдання ведуться в Trello. Баги, знайдені тестуванням, заводяться як GitHub Issues зі скріншотами й кроками відтворення.
- Пріоритети функцій: P0 (без цього MVP не існує), P1 (робимо, якщо P0 стабільні), P2 (лише за наявності часу). Не починай P1/P2, поки не готові P0.

## Тестування й критерії готовності

- Перед PR локально проходять лінтер і тести своєї папки.
- CI у GitHub Actions: лінтинг, pytest, oxlint, білд. PR не зливаємо з червоним pipeline.
- Критично тестується перекличка класу й офлайн-режим, де не можна допустити втрати даних. Тести мають емулювати обрив мережі.
- MVP готовий, коли головний сценарій проходить на реальних пристроях (телефон, планшет, ноутбук вчителя) з вимкненим інтернетом.
