# ShelterED — Технічне завдання

## 1. Тема та мета проекту

**Тема:** ShelterED — освітній хаб за принципом offline-first, що перетворює вимушений час в укритті на безпечне, тихе й корисне навчання.

**Мета:** за 2 місяці (до 12 грудня 2026) створити працюючий MVP у вигляді PWA для учнів, вчителів, батьків і адміністрації школи. Застосунок має працювати без інтернету та без світла в мережі, а коли зв'язок з'являється — синхронізувати прогрес із хмарою.

**Головний сценарій MVP:** починається тривога → учні в укритті продовжують урок із матеріалами, підготовленими вчителем → клас відмічається «я в укритті» → результати лишаються на пристроях і локальному сервері → з появою мережі все синхронізується в хмару без втрати даних.

MVP вважається готовим, якщо цей сценарій проходить від початку до кінця на реальних пристроях (планшет, телефони, ноутбук вчителя) з вимкненим інтернетом.

## 2. Проблема та цільова аудиторія

У прифронтових регіонах повітряні тривоги, обстріли й відключення світла руйнують класичне навчання: діти годинами сидять в укриттях без зв'язку, пропускають уроки й накопичують освітні втрати та хронічний стрес. Zoom і Google Meet залежать від світла та інтернету й під час сирен не працюють.

| Група | Що їй потрібно від ShelterED |
| --- | --- |
| Учні | Продовжити урок в укритті без мережі: короткі модулі, тести, мікро-відео, ШІ-репетитор, спокійний інтерфейс |
| Вчителі | Підготувати матеріали наперед, бачити статус класу й прогалини в знаннях, збирати роботи без інтернету |
| Батьки | Знати, що дитина в безпеці, і бачити прогрес та час навчання |
| Адміністрація школи | Бачити, скільки дітей в укритті, і вести журнал тривог |

## 3. Технології

| Шар | Технології |
| --- | --- |
| Frontend (PWA) | React, TypeScript, Vite, Tailwind CSS, Redux Toolkit / RTK Query, Service Worker, IndexedDB |
| Backend (хмара) | Python, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic |
| База даних | PostgreSQL (хмара і локальний сервер) |
| Черги та фонові задачі | Celery + Redis, вебхуки |
| Авторизація | JWT, OAuth 2.0 PKCE, ролі |
| AI | RAG-пайплайн, LLM через API у хмарі, легка локальна модель на ноутбуці вчителя, кеш готових пояснень |
| Локальний сервер укриття | Python (FastAPI) або C++ за потреби, Wi-Fi точка, локальний вебсервер |
| DevOps | Docker, Docker Compose, Nginx, GitHub Actions, GHCR |
| Якість коду | Ruff / Flake8, pytest, ESLint, Playwright для E2E |
| Дизайн | Figma |

Окремо погодити до кінця першого тижня: яку саме локальну модель запускаємо на ноутбуці вчителя й чи вистачає на це заліза. Якщо ні, ШІ-репетитор в укритті працює лише на закешованих поясненнях.

## 4. Основний функціонал MVP

Пріоритети: **P0** — без цього MVP не існує, **P1** — робимо, якщо P0 стабільні, **P2** — лише за наявності часу.

| № | Модуль | Що має працювати | Пріоритет |
| --- | --- | --- | --- |
| 1 | «Урок продовжується» | Застосунок знає розклад класу й отримує дані з API повітряних тривог. Коли тривога починається посеред уроку, учень одразу бачить матеріали саме цього уроку | P0 |
| 2 | Режим «Укриття» (offline-first) | Пакети знань на день завантажуються наперед. Теорія, тести й мікро-відео відкриваються без інтернету | P0 |
| 3 | Локальний сервер укриття | Ноутбук вчителя роздає Wi-Fi, учні відкривають адресу в браузері, отримують завдання й здають роботи без інтернету | P0 |
| 4 | Синхронізація | Відкладена черга запитів на пристрої й сервері. З появою мережі дані летять у хмару, без дублів і втрат | P0 |
| 5 | Мікронавчання | Модулі по 3–5 хвилин: інтерактивні картки, міні-тести, квести | P0 |
| 6 | Перекличка класу | Кнопки «я в безпеці» / «я в укритті». Вчитель бачить статус усього класу, батьки — свою дитину. Без інтернету статус іде через локальний сервер або в чергу | P0 |
| 7 | Тихий режим | Усі відео з субтитрами, кожне завдання можна пройти без звуку | P0 |
| 8 | Ролі та кабінети | Учень, вчитель, батьки, адміністрація школи, кожен зі своїм інтерфейсом | P0 |
| 9 | Енергоменеджер | Темна тема, мінімум анімацій. Прогноз «заряду вистачить приблизно на 40 хвилин навчання» | P0 (тема й анімації), P2 (прогноз) |
| 10 | Офлайн-довідник безпеки | Покрокові інструкції з першої допомоги та дій у надзвичайних ситуаціях, доступні однією кнопкою без мережі | P1 |
| 11 | ШІ-репетитор | Пояснює пропущену тему іншими словами, розбирає помилки в тестах. В укритті працює на локальній моделі або закешованих поясненнях | P1 |
| 12 | Мапа знань і адаптивні траєкторії | Візуальне дерево тем із прогалинами та їхніми зв'язками. Складність підлаштовується, вчитель бачить картину по класу | P1 |
| 13 | Конструктор уроків | Вчитель збирає пакет із готових карток чи власних матеріалів і ділиться ним із колегами | P1 |
| 14 | QR-синхронізація | Якщо немає ні інтернету, ні локального сервера, учень показує QR-код зі своїм прогресом, вчитель сканує його телефоном | P1 |
| 15 | Опитування «як ти зараз?» | Коротке питання перед заняттям, дихальні вправи. ШІ готує зведення для психолога й батьків | P1 |
| 16 | Кооперативні квести | Діти в одному укритті розв'язують спільну задачу командою через локальний сервер | P2 |
| 17 | Дашборд школи й аналітика втраченого часу | Скільки дітей в укритті, журнал тривог, години навчання, що припали на тривоги | P2 |

**Обмеження для модуля 15.** Система не ставить діагнозів і не оцінює стан дитини як медичний. Вона збирає мінімум даних, показує лише узагальнені сигнали й делікатно пропонує звернутися до шкільного психолога. Формулювання питань і порогів погоджуємо з психологом до релізу.

## 5. Ролі користувачів

| Роль | Може | Не може |
| --- | --- | --- |
| Учень | Проходити уроки й тести, відмічатися в перекличці, питати ШІ-репетитора, бачити власну мапу знань | Бачити дані інших учнів |
| Вчитель | Створювати й публікувати уроки, бачити статус і прогалини свого класу, запускати перекличку й тренувальну тривогу, синхронізувати локальний сервер із хмарою | Бачити інші класи без доступу |
| Батьки | Бачити статус безпеки й прогрес своєї дитини, отримувати зведення | Бачити інших дітей |
| Адміністрація школи | Бачити дашборд безпеки, журнал тривог, керувати класами та користувачами | Редагувати навчальний контент вчителів |

Усі ролі працюють через JWT із розмежуванням доступу на рівні API. На локальному сервері діє той самий набір ролей із кешем прав, виданих у хмарі.

## 6. Розробники (6 осіб)

### Розробник 1 — Роман — AI & Intelligence Core

- RAG-пайплайн для генерації й адаптації матеріалів: інструкції з безпеки, персоналізовані пояснення прогалин із мапи знань.
- ШІ-репетитор: API для чату, режим «пояснити іншими словами», розбір помилок у тестах. Варіант для укриття: кеш готових пояснень і легка локальна модель.
- AI-модуль опитування «як ти зараз?»: делікатна оцінка стану за узагальненими сигналами, без діагнозів. Сумаризація звітів для психологів і батьків.
- Парсинг і класифікація сповіщень з API повітряних тривог (початок, відбій, регіон) та передача події в backend.
- Результат: AI-сервіс із документованим API й набором тестових промптів для перевірки якості відповідей.

### Розробник 2 — Стас — Backend Architecture & Core API

- Основний backend на FastAPI, PostgreSQL через SQLAlchemy 2.0, міграції Alembic.
- Модель даних: школа, клас, розклад, урок, пакет знань, результат, статус переклички, журнал тривог.
- Синхронізація: протокол обміну між хмарою, локальним сервером і клієнтом, ідемпотентні запити, відкладені черги, Celery + Redis, вебхуки.
- Авторизація: JWT, OAuth 2.0 PKCE, ролі «учень / вчитель / батьки / адміністрація».
- Результат: OpenAPI-специфікація до кінця 1-го тижня, щоб фронтенд і AI працювали паралельно.

### Розробник 3 — Данило — DevOps, Infrastructure & автоматизація тестування

- Docker і Docker Compose для розгортання на ноутбуці вчителя й на хмарному сервері. Один образ із двома профілями: `cloud` та `shelter`.
- CI/CD у GitHub Actions: Ruff/Flake8, pytest, ESLint, білд і пуш образів у GHCR.
- Nginx як реверс-проксі: роздача PWA, API та локального трафіку в укритті.
- Автоматизовані E2E-тести (Playwright) і тести синхронізації з емуляцією обриву мережі.
- Результат: розгортання на чистій машині однією командою та зелений pipeline для кожного pull request.

### Розробник 4 — Максим — Frontend & Client Experience

- PWA на React, TypeScript, Vite, Tailwind CSS: Service Worker, IndexedDB, офлайн-кеш пакетів знань.
- Інтерфейси ролей: учень, вчитель, батьки, адміністрація. Дашборди з динамічними даними.
- Енергоменеджер: темна тема, мінімум анімацій, оптимізація заряду.
- Інтерактив: мікро-модулі, кооперативні квести, мапа знань, конструктор уроків для вчителів, перекличка.
- QR-синхронізація: генерація коду на пристрої учня, сканування на пристрої вчителя.
- Результат: PWA, що встановлюється на телефон і повністю працює без мережі після першого завантаження.

### Розробник 5 — Олег — System Integration & Fallback

- Локальний сервер укриття на Python (C++ лише за потреби): Wi-Fi точка на ноутбуці вчителя, локальний вебсервер, зрозуміла адреса для учнів.
- Локальне сховище й черга подій, які пересилаються в хмару при появі мережі. Інтеграція з PostgreSQL.
- Легкі HTML/CSS/JS сторінки для найгіршого випадку, коли PWA недоступна.
- Спільна робота зі Стасом над протоколом синхронізації й з Данилом над пакуванням.
- Результат: ноутбук вчителя з вимкненим інтернетом роздає застосунок, приймає роботи та статуси перекличок і не втрачає їх після перезапуску.

### Розробник 6 — Лада — UI/UX Design & Product QA

- Дизайн-система й екрани у Figma: спокійна палітра, великі елементи керування, «Тихий режим» для укриття, де сплять діти й плачуть малюки.
- Прототипи ключових сценаріїв: тривога під час уроку, перекличка, офлайн-вхід, мапа знань.
- Повний цикл ручного тестування: тест-кейси, чек-листи, регресія на реальних пристроях.
- Пріоритет перевірки: перекличка та офлайн-режим, де не можна допустити втрати даних.
- Результат: макети до кінця 2-го тижня й тест-кейси на кожну функцію P0 до кінця її розробки.

## 8. Ризики та критерії готовності

| Ризик | Наслідок | Що робимо |
| --- | --- | --- |
| Синхронізація дублює або губить дані | Втрата відповідей, відміток переклички | Ідемпотентні запити, унікальні ідентифікатори подій на клієнті, тести з обривом мережі з 2-го спринту |
| Локальна модель не запускається на ноутбуці вчителя | ШІ-репетитор не працює в укритті | Закешовані пояснення як запасний варіант, рішення за результатом перевірки до кінця 1-го тижня |
| Wi-Fi точка на ноутбуці поводиться по-різному на різних ОС | Учні не підключаються | Рано визначити ОС ноутбука вчителя, тестувати на реальному обладнанні з 3-го спринту |
| API повітряних тривог недоступне чи змінює формат | Не спрацьовує автоперехід на урок в укритті | Ручна кнопка «Тривога» для вчителя, парсинг із валідацією |
| Забагато функцій на 2 місяці | Нічого не доведено до кінця | Жорсткі пріоритети P0 / P1 / P2, заморожування функцій на початку 4-го спринту |
| Чутливі дані дитини (стан, місцезнаходження) | Етичні та юридичні проблеми | Мінімум даних, доступ за ролями, консультація з психологом щодо формулювань |
| Мало навчального контенту | Демо виглядає порожнім | Підготувати 2–3 пакети уроків і курс безпеки для демо, щоб контент не блокував розробку |

**MVP готовий, коли виконано все:**

- Сценарій «тривога → урок в офлайні → перекличка → синхронізація» проходить на реальних пристроях без інтернету.
- Усі функції P0 мають тест-кейси, і жоден критичний дефект не відкритий.
- Розгортання локального сервера й хмари робиться однією командою за інструкцією.
- Pipeline CI зелений на основній гілці.
- Підготовлено демо та короткий опис проєкту.

## 9. Поза MVP

Ідеї, які не входять у 2 місяці, але варто описати в презентації як розвиток:

- Кілька профілів на одному пристрої для сімей із одним планшетом і звіт для батьків про час навчання.
- Курс безпеки як окремий предмет: мінна безпека, домедична допомога, тривожна валізка школяра.
- Модуль цифрової безпеки: чому не можна публікувати наслідки ударів і роботу ППО, як розпізнати фейк і вербування через месенджери.
- Навчальні тренування евакуації: вчитель запускає «тренувальну тривогу», клас проходить інтерактивний сценарій.
- Аналітика втраченого навчального часу для громад, МОН і донорів як основа B2G-моделі.
